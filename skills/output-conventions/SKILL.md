# Output Conventions

## Folder structure

All outputs go to `outputs/` at the root of the consumer project:

```
outputs/
├── audit/                   # /hormozi-gtm:audit
├── lp/                      # /hormozi-gtm:lp
├── script/                 # /hormozi-gtm:script (vsl + short)
├── plan/                   # /hormozi-gtm:plan
├── review/                  # /hormozi-gtm:review
├── hooks/                   # /hormozi-gtm:hooks
├── pricing/                 # /hormozi-gtm:pricing
├── email/                   # /hormozi-gtm:email (cold/warm/nurture/re-engagement)
├── objections/              # /hormozi-gtm:objections
├── case-studies/            # /hormozi-gtm:case-study (plural — case studies come in a series)
├── webinar/                 # /hormozi-gtm:webinar
├── positioning/             # /hormozi-gtm:positioning
├── content/                 # /hormozi-gtm:content-hub (content roadmap)
├── retention/               # /hormozi-gtm:churn-prevention (churn-analysis + winback)
└── client-onboarding/       # /hormozi-gtm:client-onboarding
```

If the folder doesn't exist, create it before writing. Never write to the project root.

## Naming convention

```
outputs/<type>/<type>-<slug>-<YYYYMMDD>-v<n>.md
```

**Examples:**
- `outputs/audit/audit-closing-course-20260519-v1.md`
- `outputs/lp/lp-revops-diagnostic-20260519-v2.md`
- `outputs/script/vsl-closing-course-20260519-v1.md`
- `outputs/script/short-closing-course-20260519-v3.md`
- `outputs/plan/plan-level-gtm-20260519-v1.md`
- `outputs/review/review-lp-client-x-20260519.md`
- `outputs/hooks/hooks-closing-course-20260519-v1.md`
- `outputs/pricing/pricing-closing-course-20260519-v2.md`
- `outputs/email/email-cold-revops-diagnostic-20260519-v1.md` (sub-type in the prefix)
- `outputs/objections/objections-revops-diagnostic-20260519-v1.md`
- `outputs/case-studies/case-study-stark-bank-20260519-v1.md`
- `outputs/webinar/webinar-revops-diagnostic-20260519-v1.md`
- `outputs/positioning/positioning-revops-diagnostic-20260519-v1.md`
- `outputs/content/content-roadmap-revops-diagnostic-20260519-v1.md`
- `outputs/retention/churn-analysis-revops-diagnostic-20260519-v1.md`
- `outputs/retention/winback-sequence-revops-diagnostic-20260519-v1.md` (exception — winback shares the folder with churn)
- `outputs/client-onboarding/onboarding-revops-diagnostic-20260519-v1.md`

**Rules:**
- `<slug>` is kebab-case, derived from the product/offer/client
- `<YYYYMMDD>` is the creation date or last major update
- `<v{n}>` auto-increments. Version 1 is never ambiguous — always `-v1`
- Never overwrite without the `--overwrite` flag
- Reviews have no `-v{n}` (one-shot)

## Standard frontmatter

Every output starts with YAML frontmatter:

```yaml
---
plugin: hormozi-gtm
plugin_version: {{plugin_version}}   # read from .claude-plugin/plugin.json at generation time
command: lp                          # init|audit|lp|script|plan|review|hooks|pricing|email|objections|case-study|webinar|positioning|content-hub|churn-prevention|client-onboarding
version: 2                           # increments on each refinement
status: draft                        # draft | approved | shipped
created: 2026-05-19T14:30:00-03:00   # ISO 8601 with TZ
client: {{company_slug}}              # = gtm-context.md:company_slug
product: {{product_slug}}             # kebab-case slug of the product/offer
frameworks:                          # skills used in production
  - grand-slam-offer
  - value-equation
  - bonus-stacking
  - guarantees
humanizer_pass: true                 # true only on external copy; false on internal/diagnostic output
humanizer_mode: full                 # full (external copy) | n/a (internal/raw)
voice: humanized                      # humanized (external copy) | raw (internal/diagnostic)
language: en                          # = gtm-context.md:language — output language of the copy (en | pt-br | ...)
audit_ref: outputs/audit/audit-ketlin-20260518-v1.md  # if applicable
pricing_ref: outputs/pricing/pricing-revops-20260518-v1.md  # if applicable
parent_version: outputs/lp/lp-revops-20260519-v1.md  # when refinement
---
```

### Load-bearing fields

- `plugin_version` → when filling the template, read `.claude-plugin/plugin.json` and replace `{{plugin_version}}` with the real value (e.g. `0.1.2`). Never hardcoded in the template.
- `humanizer_pass: false` → blocks external release (lint check). It's the correct state for every internal/diagnostic output (audit, review, plan, pricing, objections, positioning, churn analysis, onboarding) — those ship as `humanizer_mode: n/a` and `voice: raw`, and never pass through the humanizer. External copy (lp, script, hooks, email, case-study, webinar, content, winback) ships as `humanizer_pass: true` / `humanizer_mode: full` / `voice: humanized`.
- `audit_ref` → tracks whether the copy was written against an audited offer
- `parent_version` → refinement tree
- `frameworks` → lets you find "every output that used skill X"
- `language` → mirrors `gtm-context.md:language` (default `en`). Drives the output language of the generated copy. The voice and brutality rules are language-independent — the copy is written native in the target language, never translated. Internal/diagnostic outputs follow the same field for any prose they contain.

### Exception

- The `gtm-context.md` schema (persistent input, not generated output) lives in the `template-gtm-context` skill — it uses minimal frontmatter (`company_name`, `company_slug`, `last_updated`, `version`, `plugin`, `language`). No `command`/`humanizer_pass`. The `language` field there is the source of truth that every generated output mirrors.

### Placeholder convention

All skeletons (the `template-*` skills) follow the same convention to avoid ambiguity between human name and technical slug:

| Placeholder | Type | Source | Example |
|---|---|---|---|
| `{{company_name}}` | human text | `gtm-context.md` | "Ketlin Scalco" |
| `{{company_slug}}` | kebab-case slug | `gtm-context.md` | "ketlin-scalco" |
| `{{product_name}}` | human text | command input | "RevOps Diagnostic" |
| `{{product_slug}}` | kebab-case slug | command input | "revops-diagnostic" |
| `{{plugin_version}}` | SemVer version | `.claude-plugin/plugin.json` | "0.2.0" |
| `{{ISO8601}}` | timestamp | generation time | "2026-05-20T14:30:00-03:00" |
| `{{path_or_null}}` | path or null | input/context | "outputs/audit/audit-revops-20260518-v1.md" or `null` |
| `{{prior_version_path_or_null}}` | path or null | on refinements | path of the prior version or `null` if v1 |

**Rule:** never use `{{slug}}` alone (ambiguous — company? product?). Always prefix it.

### Optional fields

- `tags: [b2b, saas]`
- `assignee: henrique`
- `due: 2026-05-25`
- `feedback: outputs/review/review-lp-revops-20260520.md`

## Refinement loop

When a command is invoked with the path of an existing file:

1. Read the file's frontmatter
2. Load the context (frameworks, audit_ref, etc.)
3. Apply the user's feedback on content
4. Create a new `v{n+1}` file in the same folder
5. The `v{n+1}` frontmatter references `v{n}` in `parent_version`
6. The humanizer runs again
7. The command returns the path of the new file

## When to edit in place

The default is always versioning. Edit-in-place only with the explicit `--overwrite` flag. Scenarios:

- Typo fix
- Metadata update (status: draft → approved)
- Pre-shipment cleanup

Never use overwrite for substantial content changes.

## .gitignore recommendation

The plugin README recommends:

**Option A:** ignore versioned outputs

```
# project .gitignore
outputs/
!outputs/.gitkeep
```

**Option B:** version everything (client document)

No `.gitignore` entry. Commits follow the project's cadence.

Each project decides. The README explains the trade-off.

## TL;DR per output

Recommended but optional: each output has a `## TL;DR` section at the top (after the frontmatter) with 2-3 lines summarizing the deliverable. Helps when someone opens the file 3 weeks later.

## Invariant: telemetry never goes into the file

Orchestration telemetry (phase plan, narration of phase transitions, mode marker) belongs **strictly to the conversation channel**. It is NEVER serialized into the `outputs/` file or the frontmatter. The file contains only the deliverable.

`--quiet` only silences the conversation — it is not what protects the file. The file is protected by this rule, regardless of flags. If a command phase produces an orchestration log, that log stays in the conversation and is discarded before saving.

## Anti-patterns

- Saving output without frontmatter
- Serializing orchestration telemetry (phase plan/narration) inside the output file
- Overwriting without an explicit `--overwrite`
- Naming a file without including `v{n}`
- Saving to the project root instead of `outputs/<type>/`
- Forgetting to update `parent_version` on a refinement
- Marking `humanizer_pass: true` without having run the humanizer
